# Strata 社区经验：第二轮本机复核

2026-10-02 至 2026-10-03。继续第一轮剩下的三个上游方向。硬件仍为 AVX2 Intel HX、32GB DDR4、2080 Ti 22GB、PCIe 3.0 x16。所有请求串行，原权重、量化、top-k、32768 上下文保持不变，没有改硬件电压/频率、安装或推送。

## 采用与未采用

- **采用启动直接读取**：依据 [#362](https://github.com/Niko1221/Strata/pull/362) 的思路，适配本机 GPU 专家初始填充和 pinned RAM 填充。我们本来已有非缓存的 prefill 流式专家读取，没有整套移植 #362 的 GGUF 分片、批量合并和 decode staging。
- **采用首块 PLE 读取重叠**：[ #374 ](https://github.com/Niko1221/Strata/pull/374) 的首块读取与 layer 0 重叠，加入上传/事件错误检查；后续块保持已有的读前行为。
- **未在日常配置启用批量专家收集**：[ #439 ](https://github.com/Niko1221/Strata/pull/439)。8K/16K/31K 的四轮平均为 +4.48% / +3.61% / -1.24%，短输入波动较大，长输入回退。与 PLE 一起开也没有全面改善。试验开关和逐字节测试保留，方便复核。
- PLE 队列深度最终选择 **64**。完整模型没有一致提速，长输入出现回退，因此保留 64。下方保留完整 64/256 对照。

## 启动：相同专家驻留，ABBA 对照

| 方式 | 服务就绪时间 | GPU 专家填充 | pinned RAM 填充 |
|---|---:|---:|---:|
| 原映射 A | 80.124s | 30.202s | 11.8s |
| 直接读取 A | 28.816s | 12.510s | 8.7s |
| 直接读取 B | 26.261s | 12.398s | 9.3s |
| 返回原映射 B | 69.775s | 40.033s | 11.8s |

GPU 8974 个专家、RAM 6137 个专家（10GiB）、冷层 9465 个专家一致。专家填充合计从 **42–52s 降到 21–22s**。没有清空 Windows 文件缓存，这些是顺序启动实测，不能称作严格冷盘启动。服务就绪还包含模型初始化和端口准备，不等同于 GPU 填充时间。

本机原先已经保住完整 10GiB pinned 区，因此没有照搬上游“恢复更多 RAM 驻留后 decode 大涨”的结论。这里只改启动读取；decode 冷专家读取和原 prefill 流式读取策略不变。Windows 的对齐读缓冲还改为线程结束时释放，避免新增启动工作线程遗留缓冲。

## Prefill：同进程、完整四轮顺序平衡

四个开关组合，三个固定长度，每长度预热一次/组合，加四轮正式对照：**60 个请求，48 个正式请求**。第四轮接在原进程中，补齐每个组合在每个长度下的四种出场位置。前缀缓存关闭，逐次断言 cache_n=0；保留正常 PLE 行缓存。异步 commit 与 Turing attention 沿用上一轮配置，直接启动读取在所有组一致。

以下仅比较“不重叠”和“只开 PLE 重叠”，单位是引擎输入处理时间，包含该路径的相关工作，不是直接测量的客户端流式首 token 延迟。

| 实际输入 token | 原路径平均 | PLE 重叠平均 | 吞吐变化 |
|---:|---:|---:|---:|
| 8,390 | 15.869s | 15.900s | -0.20% |
| 15,956 | 21.474s | 21.236s | +1.12% |
| 31,243 | 41.887s | 40.026s | +4.65% |

31K 的四对速度变化：+4.94%, +4.79%, +5.25%, +3.63%。8K 平均接近零，16K 的小幅差异不应夸大。不同长度之间会改变缓存和缓冲布局，原始每轮数据已保存；不能拿初筛某次 +13% 当稳定收益。

额外重启原先的可执行文件，预热后返回对照为 8K **16.610s**、31K **43.166s**，召回正确。这只有一组正式样本，用来核查明显回退，收益主估计仍用上述四轮同进程对照。也不直接与第一轮报告的历史数字相减。

## PLE 队列深度：64 与 256

先用真实表的 PleTable.gather_batch 做组件试验：8K/32K tokens 的随机行集合、行缓存关闭、顺序交替、每长度预热 1 对 + 正式 3 对。8 对输出全部逐字节相同。组件数据变化较大，正式聚合吞吐约 +44% / +22%，不代表完整模型收益。

整模型随后固定 PLE 重叠、相同直接启动读取，四次新进程按 64→256→256→64 排列，保留正常行缓存，前缀缓存仍关闭。每次各读 8K/31K 一遍，再重复一遍，合计 **16 个请求**。首次读入包含进程与路径预热，因此独立列出。

| 标称长度 / 条件 | 64 深度时间（秒） | 256 深度时间（秒） | 聚合吞吐变化 |
|---|---:|---:|---:|
| 8192 / 每次启动后的首次读入 | 25.342 / 26.463 | 19.709 / 27.108 | +10.65% |
| 8192 / 重复读入 | 14.722 / 16.770 | 14.629 / 14.935 | +6.52% |
| 32768 / 每次启动后的首次读入 | 51.648 / 48.931 | 54.076 / 57.969 | -10.23% |
| 32768 / 重复读入 | 39.865 / 39.767 | 41.673 / 43.073 | -6.03% |

每组仅 2 次观察，需结合波动判断，不能保证其他输入或其他 SSD 同幅收益。所有请求的隐藏词召回及 cache_n 检查通过。

## 正确性与部署

- 原生批量 gather 的 9 组大小/对齐/中途组位置测试通过；Windows 分层来源在直接读取开关两侧均通过。
- 服务 API 39 项通过，包含请求开关范围校验。全套工程测试没有执行：本地已有部分测试源码/fixture 缺失，采用可单独构建的针对性目标。
- 315、595、1155、2295、4575、8390、15956、31243 tokens，四个组合，共 32 次检查：每 64 个位置抽样的最终残差逐字节一致，召回正确。这是抽样残差一致性，不是所有模型输出、所有位置和所有任务的全面质量证明。
- 生产配置下长 8K 连续/分支/返回对话实际复用超过 8000 tokens，截断后再次请求正常，额外 31K 召回通过；共 7 个请求。服务保持单请求并发、32768 上下文，最终无在途请求。
- 本次生产回归中首次 31K 请求用了 59.530s。上面约 40s 的数字来自预热后的重复输入，不能承诺日常每次长输入都达到该时间；前缀缓存状态、行缓存、文件缓存和初始化工作会影响延迟。此项生产请求是正确性回归，不与预热计时组直接相减。
- 日常启用 `--tiered-direct-load 1`、`--prefill-io-tuning 2`；队列深度 64。新优化在源码中默认关闭，明确由配置启用。正常前缀缓存已经恢复。

本轮没有重新确认 decode 吞吐收益，不把启动/prefill 改善说成 decode 提速。历史偶发 CPU 执行异常的根因仍未确认。
