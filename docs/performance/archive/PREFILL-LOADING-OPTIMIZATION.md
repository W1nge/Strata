# Prefill 加载优化：按分块大小调整预读队列

2026-10-03。已采用并恢复普通服务。单并发、原模型和 FP16 KV、32K 上下文、16K Prefill 分块、已有 Decode 优化和缓存 180 秒落盘 / 3600 秒删除策略均保留。

## 本轮采用的改动

新增 `--prefill-ring-large 384`。分块布局达到 12,288 token 时，流式专家预读队列使用 384 个 GPU 槽位；较小分块继续使用原来的 192 槽（不足 2048 的原有 8 槽路径也保留）。布局按原有规则向上取整到 256 token，阈值针对分配的分块容量，不是整段上下文长度。

长分块提前准备更多专家权重，减少 GPU 等待。最大临时借用从 4465 个专家缓存槽 / 7.21 GiB，变成 4728 槽 / 7.63 GiB，约多借用 427 MiB。预填充结束后补回专家，日常 8974 个 GPU 专家槽总容量不变。空间计算与实际布局共用同一选队列函数。该选项在源码中默认关闭，由本机配置启用。

最终只改动 Prefill 接口、队列选择和命令行参数这三个源文件，没有修改数值计算内核。

## 正式对照结果

使用本轮开始前保存的实际旧可执行文件 A，对比最终候选 B。连续顺序为 B2–A2–A3–B3，每个进程串行处理 31K、16K、8K，重复两轮。共 24 个测量请求，另有 24 个短清理请求；每个测量请求均断言前缀缓存命中为 0、目标词召回正确。测速期间关闭诊断，没有并行推理、编译、GPU 测试或重型文件作业。

下面是引擎输入处理时间的中位数。8K/16K 每组 4 个样本，31K 的首次/重复分别每组 2 个样本。Windows 文件缓存未清空，“首次”仅指该进程的第一次长输入，不是冷 SSD 测试。首字延迟和全部原始样本在 JSON 中。

| 输入 | 原版本 | 优化后 | 耗时减少 |
|---|---:|---:|---:|
| 8,390 token | 15.55 s | 13.84 s | 11.0% |
| 15,956 token | 18.62 s | 16.81 s | 9.7% |
| 31,243 token，进程内首次 | 43.97 s | 39.28 s | 10.7% |
| 31,243 token，重复完整输入 | 37.14 s | 35.73 s | 3.8% |

这些小样本存在 I/O 长尾：旧版 16K 为 17.71–19.68 秒，新版为 16.77–20.94 秒。结合前面的多组筛选，常见的 16K 耗时从约 17.7 秒降至 16.8 秒，保守看约 5%；本表中位数收益更高，但不能据此承诺每次都快约 10%。新版仍有慢请求，长尾没有消失。

8K 的队列没有改变，两组也都有慢样本；表中的差异不作为这项改动对 8K 的确定性收益。31K 重复输入的收益较小且样本少，也不外推到 256K 或其他模型。

## 没有采用的尝试与测量记录

- 固定 256 槽未显示可靠优势；固定 384 槽对短输入有波动，因此采用分块策略。
- 对齐文件直读到 pinned 缓冲虽能绕过一次拷贝，并通过逐字节及并发读取测试，但实际 16K 耗时约 35–37 秒，明显慢于原路径。单独和组合实验都未采用，相关源码已完整撤出最终版本，仅保留实验存档。
- 第一次比较遇到恢复文件时间戳导致的增量构建漏编，修复后重编所有受影响对象并重新通过测试。A1/B1 之间穿插了这次构建与读取测试，预先决定将两组仅保留作初步记录，正式表只使用之后连续的 B2–A2–A3–B3。

## 剩余瓶颈

独立诊断中的重复 31K：批处理墙钟约 32.30 秒，GPU 时间线约 31.59 秒，其中权重复制等待区间约 7.39 秒；HC read 约 6.27 秒，QSA attention 约 3.08 秒，专家 gate/up 与 down 矩阵运算区间合计约 4.76 秒。热态补回 7808.6 MiB 专家权重约 0.68 秒。原始诊断日志单独保存，不混入上面的性能样本。

主要限制仍是专家权重从 SSD / 主机内存进入 GPU 的供应，以及 GPU 上的其他 Prefill 阶段。GPU 事件区间可能包含等待主机的空闲；并行 staging 的累计时间不能与 GPU 时间直接相加，也不能仅凭 wait-copy 断言 PCIe 已饱和。32GB 系统内存无法把全部非显存专家都长期放进 pinned RAM，更大的队列只能改善重叠，不能消除这一容量限制。
