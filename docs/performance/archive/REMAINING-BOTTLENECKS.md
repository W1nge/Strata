# 当前瓶颈与下一步提速方向

2026-10-02。沿用现有 Q3 权重、专家 top-k 和 32K 上下文上限。本次只复核既有日志、源码与运行配置，没有重启服务或修改推理配置，没有重新跑性能测试。

## 结论

当前是 CPU 专家处理、GPU 执行与同步共同约束；首次访问和换主题还受到内存驻留影响。没有证据支持“AVX2 已经到极限”，也没有一个已验证的 AVX 开关可以让整机再翻倍。

36 次请求合计 5,875 token / 124.8743 秒，解码 47.05 token/s。这个速度不包含输入处理，也不是每次请求的最低保证。

## 时间花在哪里

从最终版本的逐请求日志提取 2,434 个验证窗口，按窗口数加权，逐项核对生成 token 与两组 HTTP 基准一致。每个窗口平均输出 2.414 token、耗时 51.304 ms。

| 阶段 | 平均 ms/窗口 | 占总解码时间 |
|---|---:|---:|
| CPU 专家阶段 | 21.18 | 41.3% |
| 等待 GPU 到达逐层同步点 | 20.63 | 40.2% |
| MTP/草稿生成调用 | 4.22 | 8.2% |
| 主机输入准备，包括 PLE 表读取 | 1.06 | 2.1% |
| 提交与输出 | 0.85 | 1.7% |
| 其余未单独列出的工作 | 约 3.37 | 约 6.6% |

CPU 专家阶段内部，gate/up 约 28.1% 的总解码时间，down 约 12.8%，中间量化约 0.35%。这些是上表 CPU 行的子项，不能再相加到总计。

测量边界：CPU 计时包括缺页等待、线程池调度和同步，并不全是算术；GPU 等待是主机计时，包含 GPU 执行、依赖及同步可见性，不是纯 GPU 内核耗时或 GPU 利用率。剩余部分包括 verify 的尾部同步/输出头等尚未独立计量的区间，不能直接叫作“浪费”。日志均值只有两位小数，因此派生值为近似数。

## 瓶颈随缓存状态改变

原六题首轮与后两轮的 GPU 专家命中率均约 74%，路由工作量相近：

| 原六题 | 首轮 | 后两轮合计 |
|---|---:|---:|
| 解码 token/s | 36.11 | 60.48 |
| CPU 专家 ms/窗口 | 37.92 | 12.11 |
| 其中 gate/up ms/窗口 | 32.62 | 8.07 |
| 等待 GPU ms/窗口 | 21.39 | 22.23 |
| GPU 等待占解码时间 | 30.5% | 52.7% |

专家命中率几乎不变，但 CPU 阶段明显缩短。这支持主机数据热身/驻留是首次请求的重要影响因素；尚不能将全部差值精确归为 SSD 缺页，需要逐文件硬缺页、磁盘 I/O 与 CPU 任务计时才能进一步拆分。热起来后，GPU 等待成为最大单项。

新增六题 GPU 专家命中率约 58%，CPU 负担更高，三轮合计 46.35 token/s；MTP 接受率约 62%，也低于原六题的约 71%。这两项共同解释了为何重复旧题的 60 token/s 不适合作为所有任务的预期。

## 仍然存在的容量与传输限制

- 启动记录：显存专家层 14.54 GiB、pinned 专家层 10.00 GiB、冷层 15.43 GiB。冷层是按需映射，可能已在 Windows 文件缓存中，并非每次访问都要读 SSD。
- 模型还有约 26.8 GB 的 PLE 表，需要与其他数据竞争主机内存。新增题集的请求后采样中，可用内存最低约 250 MiB；长上下文检查结束后的另一个快照约 7.48 GiB。内存压力随负载变化，不能只看空闲时的快照。
- 本次只读查询仍显示 GPU 链路为 PCIe 3.0 x4；既有实测 H2D 约 3.3 GB/s。当前动态专家交换已关闭，日志中的该类 PCIe 专家任务为 0。因此带宽限制仍影响预填充和后续策略选择，但不能把当前全部解码延迟归为 PCIe 搬专家。
- 既有最终版本的约 16K 输入检查，输入处理耗时约 27–51 秒。长文的首次响应时间需要单独优化 prefill，解码 token/s 不能代表它。

## 提速优先级

1. **先细分 GPU 与 CPU 热点。** 使用现有 `STRATA_VERIFY_PROFILE` 入口做短程诊断，并区分 GPU 内核与握手等待；CPU 按层、量化类型、每专家 token 数、驻留层和任务尾部耗时统计。诊断模式自身可能影响速度，最终收益必须在关闭额外诊断后复测。
2. **减少新主题造成的主机读取和错误缓存分配。** 定位 experts.bin 与 PLE 各自的硬缺页/I/O；用实际常用任务更新专家画像，在请求之间低频调整缓存，或者按“预计节省的 CPU 时间 / 显存字节”评估驻留。只有预期收益能摊平复制成本时才交换，不能直接恢复此前每 4 窗口的高频交换。画像必须用独立题集验证，防止只提高旧题成绩。
3. **优先优化 gate/up 的真实热点。** 检查 IQ 码本展开、NT=1 路径、多 token 分块与寄存器压力；若慢在工作分片尾部，再改线程池调度。保持压缩权重与计算语义，避免预展开数据挤占内存而抵消内核收益。
4. **重新评估投机窗口的成本。** 当前每窗口平均只产生约 2.41 个有效 token，草稿接受率随任务变化。可在稳定内存条件下比较按接受率及验证成本选择窗口的策略，并检查已有 suffix policy 的作用。需要保持主模型验收；此前直接加大 spec 或把 min-p 降到 0 并未证明更快。
5. **单独优化长输入。** 核实实际客户端能否复用已缓存的对话前缀，减少不必要的重复 prefill；再测跨 chunk 专家复用与读取/传输重叠。该方向改善首次响应，不等于提高热态 decode 速度。

每次候选都应分别报告首次新主题、重复主题和长上下文后的表现，并保持后台负载可比、保留慢请求；不能用连续热身后的一组峰值判定胜出。

## AVX 与硬件选择

本机支持 AVX2 与 AVX-VNNI，不支持 AVX-512。Q2 AVX-VNNI 已实现并通过对拍，但之前未证明端到端收益，目前仍默认关闭。现有整机计时中的 down 还包含其他类型，并不全由 Q2 VNNI 覆盖。

数量级示例：即使把合计占比 12.8% 的全部 down 都加速到 1.2 倍、其余时间固定，总速度也只增加约 2.2%；实际 Q2 子集的覆盖率更小。单核缓存内微基准不能代表整机表现。内存压力修复后做一次受控 VNNI A/B 仍有价值，但应视作小收益候选。

若愿意升级硬件，优先评估兼容的 64 GB 或更大内存，以减少新主题和长上下文后的停顿；64 GB 不保证把专家、PLE、操作系统和所有缓存完全常驻，也不保证热态速度翻倍。若目标是继续提高热态速度，则同时评估更快且更大显存的 GPU，以及可用的更宽 PCIe 链路。当前 x4 的原因需要检查实际插槽、转接和通道布线，不能假设软件可直接改成 x16。现有证据不足以建议仅为 AVX-512 标签更换 CPU。
